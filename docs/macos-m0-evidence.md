# macOS M0 native evidence and runbook

Date: 2026-09-09. **M0 native feasibility verified for the user-selected current-host baseline; expanded hardware/OS acceptance deferred.**
Design: [ADR 0025](adr/0025-macos-secure-enclave-m0.md).
Scope: [PR 1 plan](macos-support-plan.md#4-建议-pr-顺序与依赖).

## Scope correction after the attempt

The user clarified that delivery is `cargo install` only. App/PKG distribution,
Developer ID, notarization and stapling are removed from the current exit gate.
The historical measurements below remain unchanged: they cover the initial Data
Protection Keychain design only. `-34018` does not establish that all source-built
Secure Enclave CLI paths require release credentials. M0 must now validate an
appropriate source-install custody design and rebuild continuity; see ADR 0025.
That scope-only correction was followed by the native experiment recorded below.
No product backend has been enabled.

## Current-host acceptance boundary

The user has no second Apple Silicon Mac available and has explicitly chosen this
Mac as the current validation baseline: `MacBookPro18,3`, arm64, macOS 26.6.2
(build 25G83), in the logged-in user's context. Cross-Mac reference-copy rejection
is **deferred / not measured**, rather than a blocking prerequisite for continuing
local M0 work. No observation on this host counts as that negative test.

The native feasibility conclusion is confined to this host/OS. macOS 14.0 remains
a compilation/deployment floor, not an accepted runtime minimum. Other Apple
Silicon models/OS versions, Intel + T2 and pre-first-unlock/logged-out service
contexts remain outside the current baseline. Real age/GUI integration and Android
versus iPhone evidence still belong to their product implementation/acceptance PRs.
This scope adjustment neither enables a product backend nor expands public support.

## CryptoKit source-install follow-up (2026-09-09)

The same Mac (model `MacBookPro18,3`, arm64, macOS 26.6.2 / 25G83) successfully
ran a different, explicitly selected research candidate. No automatic fallback was
added to the original probe. The standalone Swift experiment created two hardware
keys and reopened them from opaque references in a second process. Swift was 6.3.3
(`swiftlang-6.3.3.1.3`, clang 2100.1.1.101), Xcode 26.6, Rust 1.96.0.

The self-contained [`macos-cargo-probe`](../scripts/macos-cargo-probe/README.md)
then statically linked that Swift code behind a small Rust launcher. Its independent
Cargo archive was extracted outside the repository; the full native lifecycle ran
again from that extracted source using `cargo install --locked --offline --force`.
Both builds had `Signature=adhoc`, `TeamIdentifier=not set`, and no entitlements.
No manual code signing, profile, helper executable, App bundle or Keychain item was
needed. The provisional deployment target was 14.0; runtime was only 26.6.2.

| --- | --- |
| Tested source `.crate` archive | `81273c4f80520f70461aaff896b98cd0fe7ee4a830bbcbdabfd23a13814bf621` |
| Installed build A, Swift `-Onone` | `a93b8512366c8b0a4e80b9aecf893c948bd64494519712478ff66f006657ce0c` |
| Installed build B, Swift `-O` | `3f555af6b5a5504ef17c6809a2580b2d1b0de94f50a620a454a954ada2b37a32` |
| Rust 1.88 archive run, build A | `1f298698117bf41ba9457bbee47e2c9788fda7bb488f96db184a95a4138d14c1` |
| Rust 1.88 archive run, build B | `2703c9bbd9622ca5b43cfa4a09b1e7a434730faadba3d06e0c9d39b01ac4dece` |

The full archive lifecycle also passed with installed Rust 1.88.0 selected via
`RUSTUP_TOOLCHAIN=1.88.0`. The public Rust verifier remained the workspace build;
this is fixture MSRV evidence, not a new whole-workspace MSRV result.

All installed binaries and wrapped-reference test files were confined to temporary
directories and removed after the run. These are research artifacts, not a release.
The runner compared both public keys across processes, force install, uninstall and
reinstall, and verified independence of a second scope. The separate Rust verifier
checked ECDSA over the intended SHA-256 digest, DER → fixed 64-byte low-S conversion,
wrong-digest/wrong-key rejection, binding, and the SHA-256 of a raw big-endian ECDH
result against Rust `p256` using a fixed synthetic peer. Raw shared results and
private references were never logged or sent to the Rust verifier.

Native negatives passed for missing selection, duplicate/partial creation, empty,
raw-scalar, oversized, truncated and altered references, a different scope's
selection key, swapped roles, wrong public binding, mode 0644, symlink and hard link.
Opening never generated a replacement. These are fixture checks, not product
protocol/state-format or complete filesystem-race tests.

**Observed limitation:** removing all reference files made opening fail; restoring
copies retained for this synthetic test restored the same keys on this Mac.
Different ad-hoc builds could also use the same references. Consequently there is
no application-signature isolation or irreversible hardware destruction claim.
Cleanup removed exact local files and preserved the other test scope. This aligns
with phone-side revocation being authoritative, but replay rollback and restored
deletion-pending state still need product review. File cleanup is not key revocation.

Apple describes CryptoKit's Secure Enclave representation as encrypted material
restorable by the same enclave, not the raw private key
([Apple documentation](https://developer.apple.com/documentation/cryptokit/storing-cryptokit-keys-in-the-keychain)).
The successful native operations support API feasibility; they do not replace an
independent wrong-Mac test or an audit of key non-exportability and FFI ownership.

Reproduce explicitly from the repository root:

```sh
cargo build --locked -p age-plugin-phone-platform-keys --example macos-cryptokit-verify
python3 -B scripts/test-macos-cryptokit-probe.py \
  --fixture scripts/macos-cargo-probe \
  --rust-verifier target/debug/examples/macos-cryptokit-verify
```

To check archive independence, first use `cargo package --allow-dirty --no-verify
--locked --offline --manifest-path scripts/macos-cargo-probe/Cargo.toml`, safely
extract that `.crate` into a new directory, and pass the extracted package directory
as `--fixture`. The native runner creates its own temporary install root and states;
do not point it at user pairing state. The fixture is unpublished and separate from
the four product crates. This is not a registry install or production-plugin test.

## Current-host follow-up: CLT, concurrency and process loss

With `DEVELOPER_DIR=/Library/Developer/CommandLineTools` and
`RUSTUP_TOOLCHAIN=1.88.0`, the full native runner passed again. `xcrun` resolved
its SDK under `/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk` (SDK 26.5); Swift
was 6.3.3. No SDKROOT, CC, SWIFT_EXEC or TOOLCHAINS override was set.
This selects the installed CLT toolchain on the current Mac (which also has Xcode);
it is not a clean-machine OS installation test or evidence from another Mac.
No system-wide `xcode-select` setting was changed. The fixture now tells Cargo to
rebuild its native library when `DEVELOPER_DIR` or `SDKROOT` changes, avoiding stale
native build inputs when reusing a target directory across toolchains.

- Four worker threads dispatched 16 independent native-process verifications of the
  same immutable reference files. Every public binding and Rust crypto check passed.
  This is not concurrent creation or product replay serialization acceptance.
- A native process succeeded with piped stdin/stdout and only inherited basic user,

## Reproduce the original Keychain experiment

Build with a provisional deployment target (not an OS acceptance result):

```sh
MACOSX_DEPLOYMENT_TARGET=14.0 cargo build --locked \
  -p age-plugin-phone-platform-keys --example macos-key-probe
```

Retain the exact binaries, SHA-256 digests, OS/build, architecture/model, SDK,
signature/requirements/entitlements, caller chain, and safe PASS/FAIL output for each
attempt. Do not attach key references, private representations, ECDH outputs,
protocol material or QR contents. The probe emits only coarse errors and a digest
of its two public keys, which must stay identical when reopening or upgrading.

Generate a new run ID, retain it privately until cleanup, and never run two creators
with the same ID. All operations use `org.age-plugin-phone.m0.v1.<run-id>.<role>`
inside Data Protection Keychain, independent of production state. The probe's labels
are not a production reference or race-safe state format.

```sh
probe_run_id=$(python3 -c 'import secrets; print(secrets.token_hex(16))')
python3 scripts/test-macos-key-probe.py \
  target/debug/examples/macos-key-probe "$probe_run_id"
```

The runner checks missing state, creates separate native keys, compares the public
binding in a new process, rejects duplicate creation, deletes only selection,
rejects partial-state verify and repair, then precisely deletes the remaining key.
It fails on native denial and never reports a skipped hardware test as passed.
The 30-second per-process timeout terminates the subprocess; cleanup runs on ordinary
failure, timeout and Ctrl-C. SIGKILL, machine shutdown or unavailable Keychain may
leave isolated keys: retain the ID and explicitly retry exact cleanup when available:

```sh
target/debug/examples/macos-key-probe delete "$probe_run_id"
target/debug/examples/macos-key-probe verify "$probe_run_id"
# Expected after successful deletion: FAIL missing_signing (nonzero exit).
```

Never substitute a production label or delete all Keychain entries to clean a run.
Do not reuse the scope after uncertain cleanup. The standalone `verify` command
never creates keys. There is no status probe here; the product `status` must remain
non-sensitive and side-effect free, with unknown native capability reported unverified.

For a custody configuration that works with two independent source builds, add `--upgrade-binary /absolute/path/to/build-B`. This checks binding
continuity only; record both build digests and actual signing configuration separately.
The current Data Protection Keychain probe still fails in the recorded configuration;
this option does not solve that limitation. Before
final cleanup, use manual `create`/`verify` phases for lock/reboot and caller tests.
Copy only the test scope and public binding record to a second Mac: `verify` must
fail there, never `create`. A Mac with no matching key is only one negative case;
product metadata-copy rejection awaits PR 2/3. Run another independent scope in
parallel and verify it survives cleanup of the first before claiming isolation.

decisions. Old software keys cannot move into Secure Enclave: recover, establish a
