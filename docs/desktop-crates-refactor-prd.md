# PC 端四 crate 重构与 crates.io 发布 PRD

状态：重构验收完成。实施结果及候选源码摘要见
[候选验收记录](desktop-refactor-evidence.md)；未执行 crates.io 上传。

日期：2026-09-08

## 1. 背景与目标

当前 PC 端由主程序及 protocol、recipient-p256、transport、windows-cng、windows-storage
共六个 crate 构成。内部依赖仅配置本地路径，部分 Rust 测试引用包目录之外的测试向量，
尚不能直接作为完整依赖链发布到 crates.io。按操作系统继续增加专用包还会增加发布维护成本。

本次将 PC 端收敛为四个按职责划分、同步版本发布的 crate，使用户能够从 crates.io
安装 `age-plugin-phone`，并为后续 macOS 原生实现留下包内扩展位置。

目标用户是安装 PC 插件的技术用户、维护发布流程的开发者，以及未来实现平台后端的贡献者。
最终用户只安装一个 CLI，无需单独安装其余三个库。

成功标准：四个发布包组成无环、可独立获取和构建的依赖链；现有 Windows 行为、协议字节、
持久化状态及手机互操作保持兼容；新增 macOS 后端无需增加第五个发布包。

## 2. 范围与非目标

本次实施包括代码归属调整、Rust 导入和依赖更新、平台 FFI 隔离、测试资源归档、包元数据、
发布预检、CI 与安装及发布文档。手机 Rust 层同步更新依赖；手机应用和 Tauri 原生插件
设置 `publish = false`。

本次不实现 macOS Secure Enclave/Keychain 密钥后端，不扩大受支持平台声明，不改变手机认证、
协议、密码算法、传输策略或产品 CLI，不执行实际 crates.io 上传，也不增加自动上传工作流。
现有非 Windows 原型行为保留原有实验定位，不因重构而宣称获得硬件密钥保护。
实际发布账号、包名所有权及上传凭据在首次发布前确认，不纳入源代码。

## 3. 目标包结构与依赖

| 发布名称 | 目录 | 职责及来源 |
| --- | --- | --- |
| `age-plugin-phone` | `crates/desktop` | CLI、标准 age 接入、配对和生命周期编排；吸收原 transport |
| `age-plugin-phone-core` | `crates/core` | 合并 protocol 与 recipient-p256；保留协议、recipient、QR framing、重放状态逻辑 |
| `age-plugin-phone-platform-keys` | `crates/platform-keys` | 承接 windows-cng；容纳后续平台硬件密钥后端 |
| `age-plugin-phone-platform-storage` | `crates/platform-storage` | 承接 windows-storage 与现有 Unix 私有存储底层操作 |

允许的内部依赖方向如下；箭头表示依赖：

```text
desktop ────────────────> core ───────────────> platform-storage
   │                       ▲
   ├──> platform-keys ──────┘
   └─────────────────────────────────────────> platform-storage

mobile Rust shell ──────> core
```

`platform-storage` 不依赖其他项目 crate，`core` 不依赖 `platform-keys`，平台包不依赖 CLI
或 Tauri。操作系统专用第三方依赖使用 target 条件，不能让 Windows FFI 库进入其他平台的
实际编译路径。移动端依赖 core 不得引入桌面硬件后端。

### 3.1 主程序与 core

- 原 transport 的类型、限制、流封装及测试迁入 `desktop::transport`，更新 ADB/Wi-Fi
  调用位置；原有一次性会话、超时和路由选择行为保持不变。
- core 使用 `recipient`、`protocol` 两个公开模块承接原有 API，密码构造仍与消息协议分层。
  原有重放和 QR 子模块跟随 protocol，模块迁移不得改变域分离常量、编码或验证顺序。
- `P256Signer` 与 `P256KeyAgreement` 留在 core 的相应模块；平台密钥实现通过这些既有
  操作接口接入，不将具体 OS 句柄或可导出的私钥类型加入协议 API。
- CLI、测试、手机 Rust 层改用新包名与模块路径。删除被替代的 workspace 成员，
  不发布旧包兼容壳；这是内部 Rust 源码 API 变更，不是用户数据格式变更。

### 3.2 平台密钥

- 现有 CNG 实现迁入 `platform-keys::windows`，保留平台探测、创建、打开、删除及错误语义。
  本期保留 Windows 专用报告和类型，不强行给尚未验证的 macOS 实现设计统一能力报告。
- 现有 Windows 条件编译调用改为新包路径；Windows TPM、签名与选择密钥分离、禁止导出、
  禁止缺失时自动补建等约束不变。
- 后续 macOS 后端放入同包的 `macos` 模块并实现 core 操作接口；硬件要求、密钥生命周期、
  系统访问控制和原生验收另立设计，不添加声称可用的空实现或软件回退。

### 3.3 平台存储

- 提供 `windows` 和 `unix` 模块；本期调用方显式选择平台模块，不强求 Windows 与 Unix
  具有完全相同的文件系统语义。
- 将现有 Unix 重放及 locator 路径中的文件权限检查、锁、临时文件、原子写入和同步操作
  移入 Unix 模块。仅提取文件系统操作；路径布局、记录编码、重放范围、容量和状态转换
  仍由 core 或 desktop 的原业务归属管理。
- Windows 私有 ACL、重解析点与硬链接拒绝、独占锁和 write-through 语义保持不变；Unix
  原有权限、锁、rename 与同步语义保持不变。不借重构统一或降低两者的安全保证。
- 存储层处理有界字节和文件句柄/锁，不解析协议数据，不决定创建新配对或恢复重放状态。
  各调用方保持原有错误映射和失败后不可继续使用的行为。
- 现有 Windows IPv4 接口枚举随迁至该包的 `windows::network` 模块，保留为明确记录的
  平台辅助功能，不混入存储 API，也不为了它增加第五个包或修改发现策略。

### 3.4 安全边界

主程序和 core 继续 `unsafe_code = "forbid"`。平台包中的原生 FFI 保持小范围、可审计，
继续要求 `unsafe_op_in_unsafe_fn = "deny"`；包合并不得通过放宽 workspace lint 解决编译问题。

以下行为是重构验收约束：

- 手机长期 age 私钥不进入桌面；每次 identity unwrap 都要求全新的手机原生用户验证。
- 完整签名配对 transcript 验证及双端完整指纹比较先于信任落盘。
- 响应继续绑定配对桌面、请求摘要、一次性会话密钥与 nonce。
- 取消、认证失败、超时、断连和持久化失败均不恢复已消费的请求或响应；不确定的重放
  状态不得重建为空，打开缺失状态不得隐式创建。
- 拒绝未知协议版本、算法与消息字段；标准 `identity-v1` 边界继续忽略未知 stanza tag，
  拒绝格式错误的受支持 stanza。
- 传输可达性不构成授权；不记录私钥、文件密钥、明文、原始协议载荷或 QR 内容。

## 4. 兼容性与 crates.io 发布要求

### 4.1 用户兼容性

二进制名、命令和参数、退出行为、环境变量、`setup --json` 输出保持不变。
recipient、stanza、签名输入、二维码和流帧、磁盘编码、目录和文件名、TPM key name
均保持不变。现有有效 v2 配对升级后无需重新配对；现有不支持的旧状态继续拒绝。
重构不得以自动迁移或重置状态掩盖兼容性问题。

本次保持 workspace 当前版本及 Rust 1.88 MSRV，不顺带升级第三方依赖。
首次实际发布版本由单独的发布步骤确定，不能仅因包拆分而声称稳定版或正式 macOS 支持。

### 4.2 发布配置

- 四包继承统一版本、许可证、仓库与 MSRV；每个包有说明其用途和实验状态的 README，
  发布归档包含许可证、必要源码、测试资源及正确元数据。
- 内部依赖集中维护为 `path` 加精确版本约束；预发布阶段四包锁定同一版本。
  版本检查覆盖所有内部依赖约束及现有手机版本一致性，防止漏改。
- 四个包限制发布到 crates.io；其他两个 workspace 包禁止发布。不得用 Git 依赖、
  仓库外相对路径、发布时源码拼接或跳过验证来解决发布依赖问题。
- 手动发布固定顺序为 storage → core → keys → desktop。每步确认前置版本可从 registry
  解析后再继续；发生部分发布时停止并记录已发布版本，禁止覆盖相同版本。
- 发布文档提供显式预发布版本的安装命令：
  `cargo install age-plugin-phone --version <已发布版本> --locked`，并说明编译依赖及
  Windows 当前支持要求。安装包可构建与真实设备安全验收分别记录。

### 4.3 测试向量与归档独立性

将当前四份公共 JSON 测试向量迁入 `crates/core/test-vectors`，作为唯一来源，字节保持不变。
更新 Rust `include_str!`、Android Gradle 测试资源目录和所有文档或脚本引用；
检查 Swift 测试的向量使用方式，保留现有预期值，不因路径迁移重新生成密码学结果。
旧文档目录只保留说明与新位置链接，不保留另一份可漂移的向量。

归档必须能脱离原 checkout 构建和测试；验证不能依赖旧目录、未打包文件或手机工具链。
默认 package include 规则应排除签名材料、设备产物和其他无关文件。

## 5. 实施顺序与验收

### 5.1 实施顺序

1. 记录重构前 commit、二进制及测试基线，保存向量和 Unix 兼容夹具摘要；增加 ADR 描述
   四包职责和依赖方向。在大规模迁移前，用 Cargo 1.88 跑通第 5.2 节的最小 registry
   预检脚本，确认尚未发布的依赖链能够按规定验证。
2. 合并 core、内移 transport，更新引用和测试；保持实现行为，先通过对应测试。
3. 迁移 Windows 平台包并提取 Unix 文件系统操作，更新条件依赖，验证无循环及 FFI 隔离。
4. 整理向量和包元数据，更新 Cargo.lock、版本检查、CI、README、架构与发布文档。
5. 完成归档独立验证与可移植兼容回归，输出“源码与归档准备完成”的证据；再完成指定
   硬件上的升级和安全回归，满足第 6 节后标记“重构验收完成”。缺少硬件证据时列出
   未验证项目及原因，保留“硬件验收待完成”状态。

历史 ADR 和已发布版本证据保留历史含义，通过新的 ADR 说明包名替代关系，
不把旧验收记录改写成此次重构已经通过验收。

### 5.2 自动检查

- 执行 `cargo fmt --all --check`、
  `cargo clippy --workspace --all-targets --locked -- -D warnings`、
  `cargo test --workspace --locked`。常规 Windows CI 延续已有 TPM 硬件测试跳过名单，
  原生硬件验收单独执行，不将跳过记为通过。
- CI 检查恰好四个可发布包、内部依赖方向、精确版本一致性、非发布手机包和归档文件列表。
- 首次发布前的 registry 预检须有可重复运行的脚本，固定 Cargo 1.88，使用隔离的 Cargo
  配置、缓存及临时工作副本。脚本先以最小依赖链验证机制，再按 storage → core → keys →
  desktop 验证实际四包，解包后脱离 checkout 编译及运行可移植测试。
- 预检使用临时备用 registry：仅在临时副本中将四包的 `package.publish` 和内部依赖的
  `registry` 指向该 registry，保留精确版本；第三方依赖仍使用 crates.io。逐包打包并验证，
  确认前置包可从预检 registry 解析后再继续。不得仅设置默认 registry 就假定内部依赖
  已改用该源，也不得用 crates.io 源码替换注入尚未发布的包。
- 脚本须校验临时修改白名单：只允许上述 registry 元数据及相应锁文件来源、校验和变化；
  锁定的包名和版本不得变化，源码、测试资源和其他 manifest 字段必须保持一致。记录归档
  文件清单、内容摘要和元数据差异，检查解包后没有 checkout 路径依赖。预检配置与改写后的
  manifest 不进入正式发布包，预检包不直接上传 crates.io；正式 manifest 仍须通过第 4.2
  节的发布限制和依赖检查。最小脚本未跑通或差异超出白名单时，归档预检不得记为通过。
- registry 验证后的安装冒烟使用主包归档/registry 来源，执行 `--help`、`setup --help`，
  并运行现有 age/rage 互操作与独立恢复测试。生产 crates.io dry-run 待前置依赖上线后执行，
  不把本地 registry 成功等同于已上传成功。
- Linux、Windows 验证打包后 PC 构建；macOS 增加 PC 编译与可移植测试，保持实验平台标识。
  Android Kotlin 向量测试、Swift 协议测试和现有移动端编译检查继续通过。

### 5.3 安全与升级回归

- 既有确定性向量逐字节一致；覆盖配对取消、错误指纹、错误设备/作用域、重放、超时、
  畸形消息和未知字段，以及流截断和超长输入。
- 存储覆盖重启后重放拒绝、锁冲突、缺失/损坏状态、写入失败及 guard 失效；Windows
  覆盖 ACL 扩大、重解析点/硬链接拒绝，Unix 覆盖已有权限及同步失败语义。
- Linux 和 macOS 均运行 Unix 跨版本状态回归。以固定的重构前 commit 生成合成重放状态
  字节夹具，记录生成方式、基线版本和摘要；夹具随所属测试包归档，不由新实现在测试
  运行时重新生成。locator 包含绝对路径，因此随测试包归档固定的旧版编码生成器及基准
  输入/输出，先校验其输出与基准一致，再用该生成器写入测试临时目录的路径，交由新实现
  原样读取。生成器不得调用重构后的编码实现，也不得依赖旧 checkout 或真实用户状态。
- 新实现须打开上述旧状态，验证 locator 绑定和路径解析、未过期的已消费请求/响应拒绝、
  时钟高水位保留及后续正常持久化。使用测试时钟分别断言重放与时钟回退错误，不能以
  自然过期或其他绑定失败代替重放拒绝；同一新版代码写入后重开的测试不能替代此项。
- 在指定 Windows TPM 与手机上，用重构前二进制建立合成数据配对并消费请求，再用新二进制
  打开同一状态，验证无需重新配对、正常授权解密与已消费记录拒绝；验证取消不会恢复请求。
- 验证 TPM 双角色密钥、已有 key name 与定位记录不变；执行现有原生清理测试，确认删除
  仅作用于指定配对。手机原生认证路径不作改写。
- 任何硬件验证受环境限制时明确标记“未验证”，列出缺失证据；此时最多达到“源码与归档
  准备完成”，不得标记“重构验收完成”，不得据此扩大发布支持范围。

文档本身的交付仅需引用检查、一致性检查与 `git diff --check`；上述运行时检查是重构
实施验收要求，不代表编写本 PRD 时已经执行。

## 6. 风险与完成定义

主要风险为合并时的导入/类型冲突、core 与平台层循环依赖、Unix 存储提取改变崩溃语义、
测试资源在归档中缺失，以及四包发布的部分成功状态。通过固定依赖方向、机械迁移优先、
保持原生文件语义、脱离 checkout 测试和顺序发布控制这些风险。

完成状态分为两级：

- “源码与归档准备完成”：仓库仅有四个 PC 发布包，其余手机包禁止发布；第 5.2 节首次
  发布前可执行的检查及第 5.3 节可移植回归全部通过，包括 Unix 跨版本状态回归；预检
  归档独立可构建，正式 manifest 与预检副本的差异检查通过；文档反映实际结构并明确
  macOS 后端尚未实现。硬件项目逐项记录通过、失败或未验证及原因。
- “重构验收完成”：在前一级基础上，第 5.3 节指定 Windows TPM 与手机的升级、授权、
  重放和清理回归全部通过，原有数据和接口兼容证据齐全。任何必需硬件项目仍为未验证
  或失败时均不能达到此状态；历史版本证据不能替代本次候选版本的验收。

本文所称“重构完成”均指“重构验收完成”。crates.io 实际上线是后续发布动作；正式包的
生产 registry dry-run 在前置依赖上线后执行，预检包成功不替代该检查，实际上传成功也
不替代本次重构验收。
